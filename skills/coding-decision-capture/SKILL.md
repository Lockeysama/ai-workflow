# Coding Decision Capture

把编码过程中的上下文、取舍和验证结果整理成以后能影响行动的技术判断。目标不是记录所有实现细节，而是保留“当时为什么这样选、什么证据支持它、什么时候需要重开问题”。

## 与其他 Skill 的关系

这是编码场景的内容入口，不是运行时一定会自动调用其他 Skill 或 MCP 的编排器：

- 需要判断取舍、识别未知项或定义验证时，采用 `cognitive-settlement` 的判断方法；
- 需要交付长文、评审文档或可读 HTML 时，采用 `human-interface-language` 的表达约定；
- 用户明确要求保存到 human ai knowledge 时，交给 `haikl-knowledge-capture` 做 HIL 整理和 MCP 持久化；
- 如果只是捕获事实，不要为了完整而强行进入这两个阶段。

## 先判断是否值得捕获

优先捕获会影响未来工作的内容：

- 方案选择、架构边界、接口或数据契约；
- 被否决的替代方案及其原因；
- 造成返工、线上问题或排查成本的假设；
- 验证方式、测试结果和仍未关闭的风险；
- 以后遇到相似问题时可以复用的条件或失败信号。

实现已经明确、没有取舍、只需要补一段代码或只想保存原始日志时，直接处理或允许沉底。

## 工作方式

从现有对话、代码变更、PR、错误信息和测试结果中提取事实，不把猜测写成已经发生的事情。至少回答：

1. 当时要解决什么问题，约束是什么？
2. 考虑过哪些方案，为什么选择当前方案？
3. 哪些内容是事实，哪些仍是待验证假设？
4. 如何验证，结果是什么？
5. 这条判断适用于什么相近场景，什么信号出现时需要重开？

如果材料不足，明确列出缺口，不编造决策过程。不要把代码 diff 自动解释成架构意图；让用户确认无法从证据推出的关键判断。

## 输出形态

根据用途选择短记录或完整文档。默认结构如下，可按材料裁剪：

```text
技术问题
背景与约束
当前决策
考虑过的替代方案
决策依据
验证与结果
已知风险 / 未决问题
适用边界与重开条件
后续行动
```

如果存在真实取舍，继续使用认知结算的方法给出暂时判断、边界和最小验证；如果用户要求报告、方案或知识库交付，再使用 HIL 的分层表达。不要为了套模板补齐不存在的依据、风险或行动。

## 质量检查

- 决策是否与实际代码、配置、测试或讨论证据对应？
- 是否区分事实、解释、假设和建议？
- 是否记录了被放弃的方案及放弃条件？
- 是否留下可观察的验证结果，而不是只写“应该可以”？
- 是否写明适用边界和未来重开条件？
- 这条记录是否真的会帮助下一次编码、评审或排查？如果不会，允许不沉淀。
